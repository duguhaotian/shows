DeltaBox：在 Agent 动作之间同步回滚进程与文件

Yunpeng Dong 等 · 上海交通大学 / 华为 · arXiv:2605.22781v3（2026-11-13 修订）

论文全文：DeltaBox: Millisecond-Scale Sandbox Checkpoint and Rollback for Stateful AI Agents · 版本记录 · SIGOPS ATC 2026 官方录用与最佳论文名单。以下实验数字按 arXiv v3 解读，未独立复现。

一句话：如果 Agent 能在每次动作结束后提供一个静止点，DeltaBox 可把文件版本和进程状态配对，在同一台已运行的 Firecracker microVM 内快速回退；如果要在不改造应用的前提下分出已运行的工具，昨天的 TimeTravelContainer 关注的是另一种接口和状态边界。

1. 论文发现了什么问题？

写代码的 Agent 在搜索树中回到旧节点时，文件改动、解释器变量、打开的文件描述符和已加载的工具状态必须回到同一时刻。只恢复代码，进程仍可能沿用新分支的内存或描述符；只恢复进程，打开的路径又可能指向后来版本。两者都一致才算回到原节点。

连续节点通常只改少量状态，但常见做法仍需复制目录、重放命令，或恢复整个虚拟机。SWE-bench Verified 的 30 轮搜索轨迹中，作者平均记录了 26.4 次检查点和 27.8 次恢复，逐次开销会累积。该数字描述论文轨迹，不代表任意 Agent。§6.1 设置

2. 现有方案怎么做，有什么缺点？

  • 版本控制或文件快照：可快速隔离仓库改动，适合无长驻状态、可廉价重建的任务。Git worktree 或文件系统快照不会自行还原进程内存、线程和打开的描述符；用重放补状态又会增加成本。
  • 进程检查点 + 文件备份：CRIU 能保存进程树，但文件版本需另外对齐。论文的 CRIU+cp 控制组用 rsync 硬链接快照与 CRIU lazy-pages。恢复须等文件路径可用，不能把该实现的开销当作所有 CRIU 方案的上限。
  • 整个沙箱或 VM 快照：E2B 官方快照支持持久化文件与内存，随后创建新沙箱；Firecracker 的快照接口提供 VM 级状态和内存，外部磁盘的正确版本仍需按恢复合同管理。每分支独立 VM 适合需要不同隔离边界的场景。论文实际用自托管 E2B 增量版、CubeSandbox v0.3.0 等特定实现跟进程级分支比较，不是当前托管服务速度排名。全部控制组

3. 论文方案怎么解决，优势是什么？

DeltaState 以同一个检查点 ID 绑定两份状态。DeltaFS 是 guest 内修改的 overlayfs 模块：把当前可写层冻结、换上新的写入层，回退时原地切换到目标层链。DeltaCR 在协作式 Agent 的动作边界冻结一个模板供快速进程 fork，另做后台增量 CRIU 转储。恢复时协调器可以并行重建文件视图和进程，但下一个动作必须等两者配对。§3 工作流 · §4 实现

4. 引入了哪些新问题、还有什么没解决？

  • 热路径要求协作。有未收束的线程或子进程时，原型跳过热模板，用 CRIU 捕获进程树；模板淘汰后也走慢路径。如果后台转储没完成，恢复可能还得等；惰性恢复后第一次读页又会产生开销。需分别统计模板命中、淘汰、后台转储未完成与恢复后真实工作耗时。
  • 分支不是租户安全边界。同一 VM 里的分支共享 guest 内核、网络代理和非托管文件域。回滚无法撤销已经提交的远程写入；跨任务隔离仍按实际威胁模型选择 VM 或其他边界。
  • 要付维护和资源账。guest 侧补丁、模板驻留、增量链、CoW 脏页和深层文件查找都有开销。作者的 61 项文件语义检查是受控覆盖，不是任意工具、外置状态或长期高密运行的验证。作者未展示 stock Kubernetes/containerd/gVisor 上的相同指标。

和昨天的方案怎么选？能把动作结束约束成合作式静止点，且要频繁返回已有节点，优先研究 DeltaBox。需要保留已加载、无此接口的工具会话，优先研究 TimeTravelContainer 的 gVisor 派生活分支。两者共享的内核/运行时层次不同，公开数字不可直接比较。

可复用的验证矩阵：在可控工作负载中写入可核对的内存和文件标记，分别运行只读为主、写密集，以及模板命中/淘汰。固定 CPU、内存和分支数，量接口返回、首个/全部子分支的正确结果、家族峰值宿主内存、超时和失败。修改一个分支后重新核对父分支与兄弟分支；把异步转储完成单列为持久回退就绪，避免让热点路径的数字掩盖其他成本。这是测试设计，未在用户集群运行。
