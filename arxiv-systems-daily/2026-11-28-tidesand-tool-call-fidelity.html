TideSand：高密沙箱里，结果正确也可能测错性能

Shulu Li、Hanchen Li 等 · arXiv:2611.31118v1 · 初版 2026-11-23 · cs.OS

论文全文：TideSand: Performance-Accurate Sandbox Multiplexing for LLM Agents · 版本记录 · 作者代码。以下实验为论文报告，未独立复现。

一句话：要让高密度沙箱支持性能优化型 Agent，不能只测「每小时有多少调用跑完」。还要测同一工具在拥挤和安静环境中会不会给出不同的性能判断。TideSand 宁可先排队，也尽量不让工具在资源不足时开始计时。

1. 论文发现了什么问题？

Agent 等模型回复时 CPU 往往空闲，但沙箱的内存仍然驻留。一批回复同时到达后，编译、分析、性能测试等工具会集中争夺 CPU、内存带宽或换页 I/O。平均利用率不高，也可能在一次工具调用的窗口内严重拥挤。

在 AlgoTune 这类工作负载中，工具产物完全正确，测到的耗时却可能反映邻居的负载，而不是代码变化。§3、图 5在缩减资源的对照下观察到同一批工具调用更慢、离散程度更高；朴素超卖下，最终性能评分既可能偏低，也可能偏高。高分不自动等于测量更可信。

2. 当前方案有哪些缺点？

  • 严格预留。按配置的 CPU/内存决定是否整沙箱入场。对需要稳定对照的测量有用，但工具空闲期也占预留预算。Kubernetes 的 资源请求与限制和论文基线并不等价：请求用于调度，限额可以约束用量，但都不能单独保证每次工具测量无干扰。
  • 阈值超卖。论文在同一运行框架内测量的基线，在主机 CPU 和内存实测低于阈值时接收更多沙箱；放进去以后不对工具单独准入。它能利用空档，但短时资源需求未进入采样时，多次调用可能同时开跑。该策略与 DSec 部分思路相似，不等于完整 DSec 对比。
  • 按优先级分配权重。论文移植的 AgentCgroup 控制环按提示给工具不同 CPU 权重和内存配额、压力时保护较高类别。适合有优先级的共享场景，但被压制的任务仍可能带着干扰跑完，无法直接替代独占参考。gVisor 或 microVM 提供另一层隔离，不能仅凭隔离方式推断工具计时稳定。

3. TideSand 的方案有哪些优势？

核心机制：用模型响应作为工具执行的准入信号

为何不直接看利用率？对重工具，调度器用近期调用峰值估计需求，并暂时对已放行、还没反映在采样中的预留补账，避免同一份余量被多次使用。§4.2 用 CPU 与内存流量分别做约束，论文阈值为 70% 与 80%；已识别的轻工具可绕过重工具的 CPU 准入。§4.4 只在选定条件下于模型请求时做进程和可写层检查点，持续过载才回滚，避免常态下为每次调用付复原代价。

4. 会不会引入新问题？

  • 把执行抖动换成排队成本。工具跑得更稳定，用户仍可能等更久。年轻的小请求可以先于装不下的老请求放行；大任务的等待尾部和饥饿风险需要单独观察，论文主吞吐指标没有覆盖最后完成阶段。
  • 带宽估计和换页不是免费。CPU 与内存流量预测可能错过新型尖峰；回收、换入和检查点也会消耗磁盘、内存和 CPU。论文的 Graviton3 环境、换页盘和阈值不是 Kubernetes/containerd/gVisor 的参数建议。原型能映射 Kubernetes Pod，并不证明 gVisor 具备同一套恢复与隔离语义。
  • 回放不等于在线闭环。录制响应降低了策略对比的噪声，但不能回答实时 Agent 会如何根据被扰动的耗时改变下一步。在代理加排队也会影响流式体验。回滚进程与可写层还不能撤回已提交的远端写入；只对无外部副作用或有明确幂等协议的调用考虑重放。

落地验证：先找出结果虽对、性能判断却翻转的密度

  1. 在隔离测试环境固定节点、镜像、配额、数据与输出验收。为同一个优化前/后版本分别做低干扰参考和逐级加压；每级保持配对并随机或交错执行，记录缓存状态和邻居负载。
  2. 每次记录队列等待、工具执行、到首次核验成果的端到端耗时。按原始请求计截止前成功率，不把慢、失败或重试的调用从分母删掉。对齐实际 cgroup 的 CPU throttling、CPU/内存/I/O PSI、换页和主机资源；指标缺失标记为缺失。
  3. 同时报告输出正确率、相对低干扰分布的耗时偏移和优化排名是否稳定。若安静时 A→B 从 1.01 s 变 0.90 s，混载时却从 1.05 s 变 1.15 s（虚构示例），应先查干扰与样本范围，而不是据后者回滚代码。先建立这一判据，再决定是否需要工具级准入或换页。

与上一期的区别：DeltaBox关注动作边界上的低成本状态回退；TideSand 关注多沙箱争抢时的测量偏差，回滚只是一个兜底路径。两者是不同原型。
