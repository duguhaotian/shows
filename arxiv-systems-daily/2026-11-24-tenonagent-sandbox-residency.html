Agent 不必一直占着沙箱：TenonAgent 的内存超卖设计

Yifan Zhang 等 · arXiv:2611.00051v1 · cs.OS · 2026-10-11 提交 · 预印本

论文全文：TenonAgent: Virtualizing Execution Residency for Memory-Oversubscribed LLM Agents

一句话结论：把 Agent 的持久状态与沙箱驻留分开：在可恢复边界释放空闲沙箱，在动作执行期间控制同时增长的内存需求。

核心技术点

  • 动作之间，决定何时释放：先检查工作能否仅靠外置控制状态和持久化工作区重建。若可以，校验并提交与动作边界对应的恢复记录，才允许拆除；否则保留实例。可恢复不意味着必拆：压力与等待时长决定回收还是保温。下一动作就绪时，按需重建与验证；还需通过预测需求与物理内存余量的准入检查，才能开始。
  • 动作期间，控制未来增长：预测用于动作准入；实际执行时，以 cgroup 内存采样和余量估算决定调度许可。内核调度器通过 sched_ext 调整 CPU 派发机会，降低多个沙箱同时扩张的风险。暂停 CPU 不会回收已经占用的内存，也不是内存硬上限或防 OOM 保证。

论文证据

  • 图 9：Docker 下回放 ScienceAgentBench，资源为 4 vCPU / 8 GiB，按 7.2 QPS 持续提交 10 秒。TenonAgent 的整批完成时间为 7.9 分钟，无主动资源控制的 Eager 为 43.4 分钟，约 5.5 倍差距。指标包含重试，是三次回放的平均值，不是每个动作的加速比。
  • 图 13：8.6× 是一次短突发中已提交工作流的离线峰值之和除以主机内存容量。它不是同时使用 8.6 倍物理内存，更不是可持续吞吐倍数。
  • 图 14：紧急区和预防区同时设得太小，可靠性会下降，试验中仍可出现 OOM；需要为监控和限速生效的时差留出余量。

实践建议：先区分收益来自回收还是限速

以下是我们的实验建议，未运行集群或模型验证。

  1. 使用固定的动作轨迹和到达计划，分开测低负载、短突发、持续负载。至少比较始终驻留、仅在安全边界回收、回收加运行期反馈三组。保持主机内存、镜像、动作与重试策略一致。
  2. 把驻留空闲数、回收内存、重建就绪 P95、排队 P95、成批完成时间、成功率、OOM 和超时放在同一张表。对比固定负载下的尾延迟与失败，勿只看高峰并发。
  3. 先注入恢复记录写入失败，再注入重建后工作区版本不匹配：前者不应释放，后者不应派发下一动作。用确认通过的业务产物校验是否保持正确性，再考虑增大并发。

适用边界

这种重建恢复的是已持久化的环境与逻辑状态，不回放已完成动作，也不是任意进程或 VM 的内存快照。不能从外部重建的后台任务、持久 shell 或活连接，需要保持驻留；它们仍可在运行期被限速。等待很短或生命周期 I/O 较慢时，重建成本可能超过回收收益。作者在 Docker 和 Firecracker 中评估；不能直接外推到其他隔离后端或生产负载。本文是预印本阅读，未独立复现。
