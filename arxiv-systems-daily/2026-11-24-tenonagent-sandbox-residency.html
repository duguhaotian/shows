Agent 不必一直占着沙箱：TenonAgent 的内存超卖设计

Yifan Zhang 等 · arXiv:2611.00051v1 · cs.OS · 2026-10-11 提交 · 预印本

论文全文：TenonAgent: Virtualizing Execution Residency for Memory-Oversubscribed LLM Agents

一句话结论：把 Agent 的持久状态与沙箱驻留分开：在可恢复边界释放空闲沙箱，在动作执行期间控制同时增长的内存需求。

问题 · 现有方案 · 论文优势 · 新增问题

1. 论文要解决什么问题？

多个 Agent 同时运行时，工具执行会用掉大量主机内存，等待模型推理时内存需求却会下降。若保留每个沙箱，空闲实例的工作集会叠加；若想靠超卖提高密度，同一时间进入安装依赖、编译等高峰动作又会争抢余量。内存一旦吃紧，OOM 或超时引发重试，整批任务可能反而更慢。

论文解决的是执行工具的主机内存，不是模型推理的 GPU 显存，也不是租户隔离。关键在于把“Agent 活着”与“沙箱驻留”分开，同时处理等待期保留的内存和执行期新增的内存。

2. 现有方案有什么不足？

下面区分常见的工程取舍和作者实际跑过的基线。论文不是行业部署普查，也不能据此断言所有现有方案都更差。

  • 常驻复用与无管理执行：保留沙箱可减少冷启动，并保住 shell 或连接等难以重建的状态；但高并发下，等待中的沙箱也占内存。论文的 Eager 是无额外资源控制的对照，不等于所有常驻系统；作者另通过“始终驻留”消融隔离了驻留决策的影响。
  • 固定并发与全生命周期峰值预留：固定槽位便于管控，峰值预留适合需要较强可预测性的任务；两者都不能充分利用动作间的需求差异。槽位设松会放大同步峰值，设紧或按生命周期峰值预留又容易让任务排队、资源闲置。它们是作者测试的调度基线。
  • 按工具调用使用 cgroup：论文对照了 AgentCgroup，说明按动作调资源并不能自动解决空闲沙箱的驻留开销；这不是说 cgroup 无用，TenonAgent 本身也依赖 cgroup 采样。
  • 隔离与检查点是另外两层：Docker、Firecracker 提供执行隔离；用哪个后端不决定何时释放空闲内存。进程或 VM 检查点可保留更丰富的现场，但要处理快照的写入和恢复成本。TenonAgent 不尝试恢复任意进程内存，只支持符合恢复条件的动作边界。论文未给出与通用检查点方案的同条件性能对照。

依据论文 §2、§5.1、§5.8 与 §6；以上是机制对比，不是行业普及率判断。

3. TenonAgent 的方案有什么优势？

优势在于两层控制各解决一个问题：等待期释放可重建沙箱已占住的内存；执行期约束多个动作同时新增内存。内存宽裕时可保留热实例，避免“永远驻留”和“每步都重建”两个极端。

核心技术点

  • 动作之间，决定何时释放：先检查工作能否仅靠外置控制状态和持久化工作区重建。若可以，校验并提交与动作边界对应的恢复记录，才允许拆除；否则保留实例。可恢复不意味着必拆：压力与等待时长决定回收还是保温。下一动作就绪时，按需重建与验证；还需通过预测需求与物理内存余量的准入检查，才能开始。
  • 动作期间，控制未来增长：预测用于动作准入；实际执行时，以 cgroup 内存采样和余量估算决定调度许可。内核调度器通过 sched_ext 调整 CPU 派发机会，降低多个沙箱同时扩张的风险。暂停 CPU 不会回收已经占用的内存，也不是内存硬上限或防 OOM 保证。

4. 它引入了哪些新问题？

  • 状态一致性：外置工作区、产物版本和恢复记录成为恢复的依赖。写入失败必须保留旧实例；恢复内容不匹配必须阻止下一动作。后台进程、活连接等未外置状态不应尝试回收。本文建议另外核验外部副作用，不能把“恢复了文件”当成请求只执行一次的证明。
  • 恢复延迟与 I/O：回收省内存，但持久化和重建要耗时。模型返回更快、等待更短时，重建开销可能超过收益。作者对重建数量有约束，但没有将应用 I/O、CPU 争用和内存带宽统一纳入调度；并发恢复是否把瓶颈推到存储与尾延迟，是需要实测的工程推断。
  • 预测和控制成本：低估下一动作可能放行太多内存增长，高估会制造排队。表 4 的消融分别出现过度保守与 OOM，图 14 也显示安全余量过窄会失效。部署还需验证内核调度接口、采样开销和目标沙箱后端是否支持，不能把实验结果当作防 OOM 保证。

依据论文 §3.3–3.5、表 4、图 14 和 §7。存储瓶颈与外部副作用是实践推断，未独立验证。

实践建议：先区分收益来自回收还是限速

以下是我们的实验建议，未运行集群或模型验证。

  1. 使用固定的动作轨迹和到达计划，分开测低负载、短突发、持续负载。至少比较始终驻留、仅在安全边界回收、回收加运行期反馈三组。保持主机内存、镜像、动作与重试策略一致。
  2. 把驻留空闲数、回收内存、重建就绪 P95、排队 P95、成批完成时间、成功率、OOM 和超时放在同一张表。对比固定负载下的尾延迟与失败，勿只看高峰并发。
  3. 先注入恢复记录写入失败，再注入重建后工作区版本不匹配：前者不应释放，后者不应派发下一动作。用确认通过的业务产物校验是否保持正确性，再考虑增大并发。

适用边界

这种重建恢复的是已持久化的环境与逻辑状态，不回放已完成动作，也不是任意进程或 VM 的内存快照。不能从外部重建的后台任务、持久 shell 或活连接，需要保持驻留；它们仍可在运行期被限速。等待很短或生命周期 I/O 较慢时，重建成本可能超过回收收益。作者在 Docker 和 Firecracker 中评估；不能直接外推到其他隔离后端或生产负载。本文是预印本阅读，未独立复现。
