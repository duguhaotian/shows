一句话结论：[用一句话表达最有实践价值的发现。]

核心技术点 / 核心思路

写清楚文章要解决的问题、所用机制和产生效果的条件。技术型文章说明关键组件、接口或数据如何交互；方法型文章说明关键决策和因果关系。只保留有解释力的要点，不堆术语。

  • 作者明确提出：[机制或思路、为何有效，以及原文的证据或章节。]
  • 本次分析的推断（如有）：[哪一步是归纳、假设或外推，适用前提是什么？]

架构图 / 流程图（有明确结构时）

结构关系清晰时用架构图，步骤、分支或反馈明确时用流程图。标出读图顺序、组件与连接含义，并注明是作者原图信息的复述还是本次分析的重绘与推断。没有可核实的结构或流程时，删掉本栏目，不强行绘图。

图放在正文中，使用语义化 HTML/CSS 或内嵌 SVG；提供图注和等价文字说明，移动端不截断。禁止依赖外部脚本、字体或渲染服务。

适用边界

[适用与不适用场景、前提、样本或证据限制、技术栈依赖。]

后续跟进

[与历史分析的关联、待验证问题，以及后续得到的新证据。不要把建议写成已经完成的工作。]

归档规范

  • 文件名：YYYY-MM-DD-topic-slug.html。新增前检查同日期和同来源，避免重复或覆盖。
  • 维护 index.html；完成后重新读取提交文件，核对正文与链接。发布核验以本次提交对应部署（可取得时）及实际文章与索引渲染为准，不将旧部署成功或仓库源码视为本次已发布。
  • 发送通知前，核对消息中精确的文章 URL 与当天索引条目所指向且已实际核验的 Pages URL 一致；源码链接和旧文章应作为负例。此检查不能代替部署与渲染核验。
  • 核心栏目保持稳定。只有发现明确的信息缺口时才调整模板，并记录版本与变更原因；旧文章不自动重写。
  • 本系列经用户选择发布于 shows 仓库的 GitHub Pages；仅发布阅读分析，不包含私人资料或未获授权的内容。
