沙箱配额会改变 Agent 评测结果

Anthropic Engineering · Gian Segato · 2026-02-05 · 模板 v1.3

原文：Quantifying infrastructure noise in agentic coding evals

一句话结论：评测 Agent 时，把沙箱配额当实验变量。分开看基础设施错误率和任务成功率，但端到端成功率不要删除失败的试次。

核心技术点

  • 作者的观察：内存上限过紧，短时峰值也可能触发 OOM；上限放宽后，除了减少中断，也可能让原本无法完成的重依赖安装或测试跑起来。
  • 我们的推断：资源耗尽和外部平台故障不应混作一类。前者可能暴露 Agent 策略在既定预算下的代价。缺少日志或计数器时标为“未判定”，不猜根因。

实验图：固定模型、编排与任务，仅比较资源配置

原文要点

从 1× 到 3×，基础设施错误率从 5.8% 降至 2.1%（p < 0.001）。在 1× 至 3× 的有上限配置间，作者未检出任务成功率差异（p = 0.40），这不是证明各组等效。取消上限后，任务成功率比 1× 高 6 个百分点（p < 0.01）。

从 3× 到不限，基础设施错误率仅再降 1.6 个百分点，任务成功率却提升近 4 个百分点。作者据此指出，放宽预算可能改变 Agent 能采用的解法，而不只是减少运行中断。

实践建议

  1. 固定模型、提示、镜像、任务和超时，记录实际生效的 requests/limits、节点规格与放置、并发数。分批交错运行对照组，记录各组样本量与波动。
  2. 按全部计划试次统计端到端成功率，另表拆出任务失败、资源耗尽、已确认的平台故障与未知原因。内存用终止原因及 OOM 事件佐证；CPU 看配额节流指标，不把节流自动判为容器被杀。参见 Kubernetes 的 CPU 与内存上限说明。
  3. 试验前定下可接受的成功率差距。以同一组任务重复对照，估计差距及其不确定性，选能减少非预期中断且在容许差距内的最低余量；未检出显著差异，不等于已经证明等效。以上是实践建议，未重跑原实验。

适用边界

这些数字是该评测与运行环境里的观察。3× 不是通用配置，不设上限也不是上线建议。模型、任务、节点和并发改变后，需重新校准。

后续跟进

延续宿主影响评测的思路。待验证：在固定任务下，按资源证据分类后，有多少失败可由降低干扰解决，多少只有允许更重的策略才会转为成功？
