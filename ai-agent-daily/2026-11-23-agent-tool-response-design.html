工具返回要短，也要够 Agent 完成下一步

Anthropic Engineering · Ken Aizawa · 2025-09-11 · 模板 v1.3

原文：Writing effective tools for agents — with agents

一句话结论：工具输出先保留 Agent 做决定需要的信息；如果下一步必须精确取回对象，还要给可用的稳定标识。

核心技术点

  • 原文：优先展示任务相关且容易理解的信息，别让大量底层字段挤占上下文。某些后续工具需要技术标识，因此可以提供不同详略的响应。
  • 实践推断：把“人能辨认”与“工具能定位”分开设计。名称加所属范围可帮助选对对象；如果下游必须按 ID 读取，简洁档也可保留这个 ID，而不是把整个详细响应搬回来。仍无法确定用户想要哪一个，就先问清楚。
  • 边界：知道 ID 不等于取得访问或操作权限；权限仍由服务端单独检查。

原文要点

文中的 Slack 线程示例，详细响应为 206 tokens，简洁响应为 72 tokens。这只是同一示例的两种输出，不是平均节省量，且简洁示例去掉了抓取回复所需的线程标识。文章另报告内部 Asana 工具的留出集评测；它不是这两份 Slack 响应的对照，不能拿来证明删掉 ID 会提高成功率。

实践建议和合成检查

  1. 构建同一份固定数据：两个同名“发布清单”分别在文档库 A、B；两种简洁格式保留相同的名称与范围，一种带和详版相同的稳定 ID，一种省略它。
  2. 本地跑了四个确定性分支：明确文档库 B 时，带 ID 的版本精确取回并通过范围核验；无 ID 版本无法直接完成这次精确读取。不指定文档库时，两种版本都返回“需澄清”。无真实 API、无模型调用、无私人数据。
  3. 产品评测可再记录精确读取率、错对象率、必要的澄清、额外调用与输入 tokens。保留描述字段和其他条件不变，并加入支持补取 ID 的对照，避免把“不能直接取回”误报为任何流程均无法完成。

适用边界

该合成检查只证明接口依赖，不代表真实模型的选择准确率。只做摘要、不需要继续读取，通常无需返回这类标识；若有安全的补取路径，也可按需返回。不得把凭证或不必要的敏感字段一并塞进响应。

后续跟进

延续宿主中核验插件行为的做法：在目标宿主中另测“需要精确续查”和“仅需摘要”两类任务，并把接口回归与模型表现分开报告。未做这一步。
