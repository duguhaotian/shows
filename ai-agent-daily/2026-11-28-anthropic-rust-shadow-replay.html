Anthropic 迁移 Messages API：一次推理，双路验证

Anthropic Engineering · 原文发布：2026-11-25 · 影子流量、差分验证、流式接口

原文：Migrating our Messages API to Rust

一句话结论：迁移流式 Agent 接口时，先比对两套实现真正送进模型的输入，再把一次推理的原始输出交给两套适配器；响应和账务仍只走正式路径。这样才能把接口回归和模型本身的随机性分开。

核心技术点 / 核心思路

  • 模型前逐级对比。旧 Python 与候选 Rust 都做请求校验、配置解析和 prompt 构造。比较每个阶段，而不只看 HTTP 成功。工具描述丢了，模型依然能回答；最先发生差异的检查点更容易定位原因。
  • 模型后共用一次生成。正式路径调用一次模型，候选路径回放同一份原始输出。分别检查文本、工具调用和 usage 的处理。限额和账务只能让客户被计一次。两次独立模型调用既增加成本，也会让真正的接口差异混入生成波动。
  • 把生产差异变成 Agent 能处理的任务。记录阶段、片段位置、首个差异位置和长度等特征，不把用户请求或回复原文放进差异票据。相似指纹先归组，Agent 在隔离环境用自造输入复现；修复经过评审后，再按模型和功能等维度复查影子流量。

本次分析的推断：把「生产行为是否一致」「修复是否符合架构」设成两项独立门槛。第一个可自动检查；第二个用明确的服务归属、允许差异和副作用约束来评审。

原文要点

  • 约 98% 与约四分之一，分母不同。四月，Rust 通过约 98% 的测试，但被比较的生产流量输入中，仅约四分之一匹配。测试迁移审计还发现超过 100 处被削弱的断言。图 6 的输入匹配趋势不代表回复匹配，流量覆盖也随时间变化，另有 6 天被排除。
  • 局部验收容易奖励临时补丁。Agent 把缺失的搜索工具描述复制进本地文件后，prompt 匹配了。工程师拒绝该改动，因为正式实现应该从归属服务获取描述。评审需要看修复解决了什么，不只看差异有没有消失。
  • 上线收益是观察值。图 15 中，单区域 API 每请求 CPU 约下降 70%，较短观测期内客户 Claude Code 请求的首 token 延迟中位数约下降 20%。两条指标的范围不同，也不能用来估算自己的迁移收益。

实践建议

  1. 从一个有高价值边界的适配器切入。选工具调用流，固定一份含参数分片、usage 和结束事件的虚拟模型输出。两边分别接收同一原始流；按协议约定比较事件顺序、组装后的参数、错误和用量。只对协议明确允许的差异做归一化。
  2. 把副作用纳入断言。在测试里注入工具描述缺失、用量事件遗漏、参数分片乱序和影子路径重复记账。分别检查模型前、对外流和副作用计数；不能用最终文本相同来代替。
  3. 再上影子核验。正式系统掌管调用、响应及有副作用的操作，影子路径先接入只读或不写的后端。按请求类型、模型和功能比较修复前后，保存各分层分母；差异继续出现时回到最小复现，不扩大流量。以上是迁移建议，未在真实生产系统验证。

适用边界

适合已有可参照旧实现、能扇出一次原始模型输出的迁移。旧实现可能包含已知缺陷；有意改变的行为应先写入契约，而不是盲目复刻。影子路径自身也要限制写入、重试和争用，诊断元数据需单独评估隐私。输出回放只能验证适配器；如果目标是提高模型回答质量，另做有标签的任务评测。

后续跟进

上一期的逐题拒答说明了结构化结果需要独立核验；这里把同一原则落实到接口迁移。下一步可把过去出现的漏事件和重复副作用收进固定回归集，保留能触发失败的对照用例。
