把 Agent 的真实失败变成回归测试

OpenAI Cookbook · Tony Alaniz · 2026-08-03 · 模板 v1.2

原文：Iterating development workflows with Codex · Retrospective

一句话结论：复盘的终点不是多写一条提醒，而是让可复现的失败有明确的检查与回归用例。

原文要点

先只读诊断，以产物、测试与纠正记录重建“预期”和“实际”的差异；只处理有实质影响的失败，明确一位负责人。对可复现问题加入确定性验证和回归测试，再用新的真实场景验证最小改动，而非照搬整套演示脚手架。

实践建议：页面正确，交付链接却错了

以下是本次分析的应用建议，不是原文案例。

一个通用报告流程可能生成了有效 HTML，却在聊天中发出源码链接，而不是可直接阅读的网页。文件有效和交付正确是两个不同条件。

  1. 从当天带日期的索引条目取得文章链接，并实际核验该 Pages 页面。
  2. 发送前提取消息中用作“今日文章”的精确 URL，与上述已核验 URL 比较。不要只检查域名、扩展名或链接是否存在。
  3. 加入负例：把文章链接替换为仓库源码页，应拒绝；替换为旧文章，即使可访问，也应拒绝。
  4. 保留最小检查，不为了单一失败新增整套工作流。先观察它能否稳定区分正确与错误交付。

已做的验证：对三条既有消息进行了离线回放，结果依次为失败、通过、通过。这里只报告检查结果，不公开消息原文或个人信息；这不是生产流程集成，也不证明未来发送已受自动拦截保护。

适用边界

精确 URL 检查适用于已经明确目标页面的交付流程。语法正确或 URL 匹配不能代替部署状态和实际渲染核验；网页可能尚未发布、内容错误或不可读。三条离线样本只验证这几个案例，不是可靠性统计结论。

后续跟进

延续结果核验和中断恢复两篇分析，本篇把最后一步“发出正确链接”纳入检查。待验证：在新报告中，检查是否能识别源码页与旧文章，同时放行当天已发布页面。
