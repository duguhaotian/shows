让 Agent 可恢复：分离会话、编排与执行

来源：Anthropic · 发布于 2026-04-08 · 模板 v1.1

原文：Scaling Managed Agents: Decoupling the brain from the hands

一句话结论：不要让任务历史、Agent 编排和执行环境的生命周期绑在一起。

原文要点

Anthropic 将系统拆成三部分：追加式持久会话日志、可替换的 harness（模型调用与工具路由）、可重建且按需提供的沙箱。凭据不应能从沙箱读取。历史事件可按需取回，不必全部放入模型上下文。对应原文章节：Decouple the brain from the hands、The session is not Claude’s context window、Many brains, many hands。

实践建议：一次“提交成功、回执丢失”的假想恢复

以下为本次分析的假想案例与推断，不是原文案例，也不是已经完成的故障测试。

假设 GitHub 已接受当天文章与索引的提交，但 worker 在保存回执前中断。重启后不应直接重新写入，而应先对照远端日期、原文链接、正文和索引目标：

  1. 结果已匹配：复用现有提交，继续核验 Pages，不再创建重复文章。
  2. 结果不存在：按正常流程生成并提交；提交前再次读取分支状态。
  3. 结果冲突或不完整：保留已有内容，定位差异后再修复，不把同日期当成足够的成功证据。
  4. 发布确认：检查本次提交对应部署（可取得时），并检查实际文章与索引页面；仓库提交成功不等于网页发布成功。

适用边界

此思路适合会跨进程、跨工具或长时间运行的工作流，但不意味着小任务都需要复杂分布式架构。持久日志本身不能保证外部副作用“恰好执行一次”，也不会自动保存沙箱内的文件。去重、状态对账和文件持久化仍要分别设计与验证。

后续跟进

延续上一篇的结果核验原则，本篇关注中断后如何找回可靠状态。待验证：在远端提交成功、worker 未保存回执的边界注入中断，恢复流程能否识别已完成步骤并继续，而非重复写入？此处仅提出测试，尚未执行。
