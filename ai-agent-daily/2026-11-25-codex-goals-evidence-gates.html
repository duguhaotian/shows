设定 Codex Goal：让证据决定何时完成

文章元信息

原文：Using Goals in Codex；作者：Raj Pathak、Stefano Fabbri（OpenAI）；发布日期：2026-05-09。标签：多轮续跑、研究验收、定时任务。

一句话结论：路径不确定、但完成标准可验证的任务，适合交给 Codex Goal 跨轮推进；每天几点启动、报告能否发布，仍由外层流程决定。

核心技术点 / 核心思路

  • 目标是会话持久状态。Objective、生命周期、预算和进度附在当前线程，不推广到其他线程。线程空闲、没有待处理工作或排队的用户输入、目标仍激活且未耗尽预算，才有机会自动继续。纯计划不触发续跑；若续跑轮没有调用工具，系统会抑制下一次自动续跑，防止空转。
  • 先定验收依据，再选择下一步。结束前对照文件、测试、测量日志或原始文献逐项检查；不要把预算到头、获得替代证据或写完报告等同于验证通过。预算用尽时应报告已完成什么、卡在哪里、下一步需要什么。
  • 延伸判断：生成器负责把问题做下去，验收器负责核对结果。即使 Goal 标记完成，外层仍可拒绝发布，例如检查发现某个结论缺少可追溯的出处。

流程图：一次定时任务中的证据验收

原文要点

原文用一项量化论文的复现说明分级验收：可以重建定价和对冲机制，并用重新训练的模型做近似验证，但原始训练路径、随机种子和检查点不可用，无法原样重放训练。图 5–6 支持的做法是记录每条主张、验证途径、证据和剩余不确定性，而不是给整篇论文一个笼统的「已复现」。

实践建议

  1. 常规日报先用单次任务。由外部调度启动，选定来源后要求 codex exec 生成草稿和证据清单。独立核验日期、出处、数值单位、基线和测试条件；发布后单独核对可访问的网页。不要把交互式 /goal 当作 codex exec 的调度指令。
  2. 缺证据时，区分补查与阻塞。示例：草稿写「启动快 3 倍」，原文只给方案耗时，未给同条件下的基线。能找到原始图表，就回去核对；找不到就删掉倍数，注明能确认的绝对耗时和缺失项。栏目齐全不能替代这一步。
  3. 需要反复试验时才引入 Goal。典型任务是跑多次性能基准，或把论文主张逐条归类为已核实、近似、证据不足。交互式 Codex 用 /goal；自建集成可参考 App Server 的 thread/goal/set、get 和 clear 接口。设定范围与停止条件，不把重试等同于不限预算。

本节是实践建议，未对日报流程做对照实验。参见 Codex 长任务文档及 App Server：线程目标。

适用边界

Goal 适合终点清楚、但下一步由证据决定的任务。短任务、没有可验收终点的工作、固定时间触发任务，都不因加 Goal 而获益。原文是机制说明与案例，不提供对照数据来判断它比一次性运行更便宜或更准确，也没有证明模型自查能替代独立验收。

后续跟进

若要验证收益，可用同一批材料、同样的验收规则和预算比较单次任务和 Goal，记录未注明基线的结论数、错误引用数、正确报告的阻塞数，以及每份合格报告的耗时与成本。不仅统计成功产出，还要计入失败和超时。
