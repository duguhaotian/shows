Grok / Jev Harness：把建议、证据和授权拆开

分析对象：Iron Giant 的 Your Grok Bot Is Burning Money - Harness Fixes It（原文镜像）。这是工程实践长文，不是学术论文；下文用论文四问来审视其论点和证据。

一句话结论：先把可验证的完成条件和执行权限写进程序，再决定是否值得把高频、可回退的判断交给廉价模型。

1. 文章发现了什么问题？

作者观察到，Agent 往往用同一个生成模型完成写作、分流、质量判断和行动审批。容易出问题的有两点：大量小判断与生成任务共用长上下文，成本随调用次数累积；同一执行者同时自评和放行，缺乏独立的验收依据。多 Agent 时还会增加重复工作、共享文件冲突和交接丢失。文章给出了架构与场景示例，但没有给出实际 Bot 的调用分布、错误率或端到端基线；不能据此断定每个系统的主要开销都是路由。

2. 业界现有方案有哪些缺点？

  • 单 Agent + 生成模型。任务量不大或判断需要完整上下文时，组件少、更好维护。让它用自由文本输出分类结果会增加解析和重试；Structured Outputs 能解决形状约束，但不能保证判断正确或代替权限校验。
  • 纯规则。去重、路径、必填项、权限与发布状态有确定答案，直接写规则更可靠；来源可信度、模糊意图等语义判断更难穷举。对含糊案例留出复核或转交，比继续堆规则更实用。
  • 多 Agent 并行。独立任务可并行，争用同一工作区时会产生重复工作和合并冲突。Cursor 的 SQLite 实验支持协调成本值得治理，但没有对本文列出的整套方案做对照。

3. 文章提出的方案有什么优势？

核心思路：生成模型处理开放式产出，Jev 处理有预设选项的高频判断，Harness 管任务契约、证据门禁、授权和日志；有独立任务且并行收益明确时，再加专员。交接文件应保留任务目标、结果和验收证据，避免只在对话里说「已完成」。Jev 官方介绍。

把三种证据分开看

  • 作者的单位成本估算：同样的 2,000 输入 token，Grok 另计 150 输出 token。按原文所用单价，$0.0049 对 $0.000084，约 58 倍价差。这个算式不含升级、重试或人工复核，不是当前报价核验，也不是系统节省实测。
  • Cursor 的外部案例：同一 SQLite 重写任务、Grok 4.5 配置，旧 Harness 实际提前暂停、累计超过 7 万次冲突；新 Harness 跑满 4 小时不到 1,000 次。任务分解、版本控制、冲突处理等一起变动，不能归因于单一 Merge Agent，也不是对 Jev 的评测。
  • Jev 的独立预印本：评测 v2 §4.3在 22 个单步选择数据集上汇总的 ECE（预测概率与实际正确率的差距）为 0.028，逐数据集未加权均值为 0.061。可用来说明概率可以评测，但汇总值不是业务阈值。

4. 会引入什么新问题？还有什么没解决？

  • 语义误判放大。类型合法也可能选错。预印本 §5 / Table 9 中，Jev 在 134 个未见过的 ALFWorld 回合中完成 35.1%，同设定的 Qwen3.8-27B 为 54.5%；Jev 有 21 回合连续至少十次执行同一动作并得到同一结果。这是游戏基准，不是归档实测；它提醒我们把重试上限、状态核对和退避交给流程，不能只把历史塞给模型。
  • 交接和共享状态本身需要治理。工作区可能出现旧证据、多个写者覆盖文件，或者把本应局限于某个任务的资料暴露给其他执行器。按任务隔离写入，用任务 ID 和版本绑定交接物，合并前复核冲突及权限。一个汇总角色也可能成为瓶颈。
  • 高分不等于许可。低风险分不能放行发布、删除或其他有副作用的动作。固定权限、真实产物校验和必要审批在模型之外执行。文章没有验证跨模型一致性、端到端净成本或部署后的错误放行率。

落地建议：精读归档先用单 Agent + 规则：检查来源与重复、四段结构、目标目录；提交结果不明确就先只读核对，发布后从索引点开正文验证版本。只有当一种低风险判断被日志证明确实高频且昂贵，再安排影子测试。同批已标注用例中比较错放行率、复核比例、耗时和每篇验收通过的总成本。此处是建议，没有运行模型或改动流程。
