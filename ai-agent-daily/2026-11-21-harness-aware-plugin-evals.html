插件评测不能只看答案：在真实宿主里再测一遍

OpenAI Cookbook · 2026-09-23 · 模板 v1.3

Maciej Domagała、Łukasz Dragan、Michał Rdzany、Danny Wigg（OpenAI）

原文：Harness-aware evaluation of plugins

一句话结论：插件在简化环境中表现良好，不代表装进真实宿主后也能选对工具；看答案，也要看调用轨迹。

核心技术点

  • 原文：将同一批案例拆成工具逻辑、独立模型调用和产品宿主三层。工具层直接比较候选集合；另外两层把调用记录转成统一格式，再用同一评分器判定。
  • 原文：轨迹规则检查完成状态、预期工具和序列的查询与返回，以及答案非空。它不评价答案措辞或语义，也不保证调用顺序。
  • 实践推断：轨迹与答案应分别评分。需要验证操作顺序时，把顺序作为独立断言，而不是从通过率推断。

架构图：同一批案例，三条独立路径

原文要点与离线复核

按原文配套 Python 评分器离线重放随文附带的三组记录：独立循环 5/5，Codex 未收到 MCP 服务端指引 3/5，收到指引后 5/5。这次只给已有轨迹重新打分，没有启动模型或进行新一轮测量。

  • CPI：两份 Codex 答案都说没有该数据；无指引时却多次查询并尝试抓取未获支持的序列，有指引的记录只查一次、不抓取。文字相近，行为不同。
  • 模糊的“就业”：无指引的记录抓取两个候选，有指引的记录改为询问用户。这里比较的是观察到的行为，不是给澄清措辞打分。

实践建议

  1. 从覆盖缺口、候选并列、正常命中各取代表用例，先定义哪些操作必须发生、哪些不能发生。
  2. 保留改动前后的原始轨迹，并记下模型、宿主、指引版本；离线回放评分器不等于重新运行模型。
  3. 在目标客户端抽查，另设答案准确性和澄清质量量表。对涉及调用顺序的任务，单独加顺序检查。

适用边界

五个合成样例说明如何定位差异，不代表生产通过率。独立循环本身有任务指引，与 Codex 的差异不是只改变宿主的对照实验；Codex SDK 也不等于桌面客户端。原文另有 108 题的产品插件答案质量评估，数据与评分方式不同，不宜和这里的轨迹分数合并。

后续跟进

延续上一篇的回归检查：给“最终文字正确但工具行为不符”建立负例，再用一个未参与调试的新案例检验是否拦得住。此为待验证建议。
